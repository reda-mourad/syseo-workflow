# Syseo Workflow component integration

## Runtime model

The component has no datastore schema when it is mounted. All `ds.*` references in the component resolve against the host application's datastore. The catalog in this development project simulates that host schema.

The host application owns `Utilisateur` and `Patient`. Do not copy those two simulated dataclasses when installing the component.

## Required host user contract

The component expects `ds.Utilisateur` to provide:

- `xNumUser`: integer primary key used by messaging and task relations.
- `Nom`: display name.
- `Initiales`: initials displayed in message avatars.
- `Privilèges`: integer profile identifier.

Supported profile values are:

- `1`: administrator. The component grants no administrator-specific actions.
- `2`: doctor.
- `6`: nurse.

There is no secretary profile or secretary-specific workflow.

## Optional host patient contract

Patient-linked tasks expect `ds.Patient` to provide:

- `NoDossier`: integer primary key referenced by `Task.ID_Patient`.
- `Nom`: last name.
- `Prénom`: first name.
- `Date Naissance`: date shown in the patient selector.

The component does not own patient data, patient lists, meetings, or RCP workflows.

## Dataclasses to migrate

For a binary host, use the host-aware generator in
`Migration/New-HostSchemaMigration.ps1` instead of recreating the structure by
hand. See `Migration/README.md` for the backup, export, generation, import, and
verification procedure.

The generated XML adds these logical dataclasses, fields, indexes, and internal
relations to the host structure. It preserves the host's existing `Utilisateur`
and `Patient` objects. Add the six host-facing relations listed in
`Migration/HOST_RELATIONS.md` after importing the XML.

### Conversation

- `ID` (integer, primary key, sequence)
- `kind`, `name`, `created_at`, `updated_at`, `deleted_at` (text)
- `ID_creator` (integer, relation to `Utilisateur.xNumUser`)

### ConversationMember

- `ID` (integer, primary key, sequence)
- `ID_Conversation` (integer, relation to `Conversation.ID`)
- `ID_Utilisateur` (integer, relation to `Utilisateur.xNumUser`)
- `joined_at`, `left_at`, `last_received_at`, `last_read_at` (text)
- `notifications_enabled` (boolean)
- `ID_last_received_message`, `ID_last_read_message` (integer, relations to `Message.ID`)

### Message

- `ID` (integer, primary key, sequence)
- `ID_Conversation` (integer, relation to `Conversation.ID`)
- `ID_sender` (integer, relation to `Utilisateur.xNumUser`)
- `body`, `created_at`, `edited_at`, `deleted_at` (text)

### Task

- `ID` (integer, primary key, sequence)
- `description`, `due_at`, `created_at`, `updated_at`, `completed_at` (text)
- `ID_creator` (integer, relation to `Utilisateur.xNumUser`)
- `ID_Patient` (integer, optional relation to `Patient.NoDossier`)
- `ID_Conversation` (integer, relation to the task discussion `Conversation.ID`)
- `is_urgent` (boolean)

### TaskAssignee

- `ID` (integer, primary key, sequence)
- `ID_Task` (integer, relation to `Task.ID`)
- `ID_Utilisateur` (integer, relation to `Utilisateur.xNumUser`)
- `assigned_at` (text)

### Tag and TaskTag

- `Tag`: `ID`, `label`, `color`, `is_active`
- `TaskTag`: `ID`, `ID_Task`, `ID_Tag`

All `ID` fields are integer primary keys generated by sequences. Copy the indexes and relation names from `Project/Sources/catalog.4DCatalog`; the component's ORDA queries depend on those relation attributes.

## Client lifecycle

After the host identifies the current user, call:

```4d
Messaging_Client_Register($currentUserId)
```

Call `Messaging_Client_Unregister` when the client session exits. The development startup prompt is only a harness and must not replace the host application's authenticated user resolution.

## Notifications

Incoming messages and newly assigned urgent tasks use the native `DISPLAY NOTIFICATION` command. Non-urgent tasks do not display an operating-system notification. There is no retry, escalation, or SLA engine.

## Group task completion

A task has one global `completed_at` value. Any assigned user can complete the task, and that completion applies to every assignee.

## Installation verification

1. Confirm all expected dataclasses and relation attributes through `ds`.
2. Register two remote clients with different user IDs.
3. Exchange direct and group messages and verify unread/read status.
4. Verify the native incoming-message notification.
5. Right-click a message bubble and convert it into a prefilled task.
6. Assign urgent and non-urgent tasks and verify that only urgent tasks display a notification.
7. Verify that the Tasks badge counts all unfinished tasks assigned to the current user, the Messaging badge counts unread conversations, and the launcher badge is their sum. Zero-count badges must be hidden.
8. Complete a multi-assignee task from one assignee and verify it is completed for all.
9. Run `compile-test.bat` outside the sandbox under 4D 20 R7.

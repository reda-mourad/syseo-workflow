# Project Instructions

## 4D documentation requirements

For every task that reads, writes, reviews, diagnoses, or explains 4D code:

- Consult only these official 4D sources:
  - https://developer.4d.com/docs/
  - https://doc.4d.com/
  - https://blog.4d.com/
- Target 4D 20 R7, matching the project's `compatibilityVersion` value of `2070`.
- Prefer documentation written for 4D 20 R7 over current-version pages whenever behavior differs.
- If the official sources do not resolve an ambiguity, ask the user before proceeding.
- Cite the relevant official pages when reporting version-dependent technical decisions.

Treat the repository metadata as authoritative. Continue targeting 4D 20 R7 until the metadata or this instruction is deliberately changed.

## 4D coding and data-model conventions

- Always use ORDA instead of legacy 4D table, record, selection, query, and relation commands.
- Apply the following naming conventions to new data-model objects and to existing objects when they are deliberately modified:
  - Table names: singular and capitalized.
  - Primary keys: named `ID`, stored as integers, and generated by a sequence.
  - Foreign keys: named `ID_<TargetTable>`. When multiple foreign keys target the same table, replace `<TargetTable>` with a pertinent word that distinguishes the role of each foreign key.
  - Other field names: `snake_case`.
  - Many-to-one relations: preferably the target table name converted to `camelCase`; otherwise, use a pertinent `camelCase` role name.
  - One-to-many relations: preferably the pluralized target table name converted to `camelCase`; otherwise, use a pertinent plural `camelCase` role name.
  - Always generate valid UUIDs when setting the uuid attribute. The UUID must be uppercase and without hyphens.
  - Field type attribute value map:
    - 1  : boolean
    - 3  : int16
    - 4  : int32 
    - 5  : int64 
    - 6  : real 
    - 8  : date 
    - 9  : time 
    - 10 : text 
    - 12 : picture 
    - 18 : blob 
    - 21 : object 
  - Index type attribute value map:
    - 1  : b-tree
    - 3  : cluster b-tree
    - 7  : automatic
  - Here is an example of a relation:
    ```
    <relation uuid="D2A65B85E772A74CA0D005C99CD26F28" name_Nto1="company" name_1toN="employees" state="1">
      <related_field kind="source">
        <field_ref uuid="F7DD2B1A28CC294A9A0A44FBE8EF1D9E" name="ID_Company">
          <table_ref uuid="27668DA2B25E7B4A8E17D7CB371F0F4D" name="Employee"/>
        </field_ref>
      </related_field>
      <related_field kind="destination">
        <field_ref uuid="85D62B2A37498A41889F6D667E5DBF94" name="ID">
          <table_ref uuid="A6A04CE6285A2847A11E919903059316" name="Company"/>
        </field_ref>
      </related_field>
    </relation>
    ```

Do not rename existing schema objects solely to enforce these conventions unless the task explicitly requests a schema migration.

## 4D form object naming conventions

- Use semantic `camelCase` names for form objects.
- Prefix form object names according to their type:
  - Checkboxes: `chk`
  - Radio buttons: `rdb`
  - List boxes: `lb`
  - Buttons: `btn`
  - Rectangles: `bg`
  - Inputs: `input`
  - Text objects: `txt`
- When renaming a form object, update every reference in 4D code and in form metadata such as editor groups and views.

## 4D compilation verification

- After writing or modifying 4D code, run `compile-test.bat` from the repository root.
- **Always run `compile-test.bat` outside the sandbox. Never attempt to run it in a sandboxed process.** The 4D compiler cannot execute properly inside the sandbox, and a sandboxed run can fail without producing valid compiler diagnostics.
- Request the required elevated/unsandboxed execution permission before running the compilation script when it has not already been granted.
- Treat the task as complete only after reporting whether the compilation check passed or failed.
- If compilation fails, inspect the reported diagnostics and fix errors caused by the current change before completing the task.
